## 1. CPU vs GPU — 동시성 1 (2026-11-27)

**같은 노드, 같은 이미지, `OCR_DEVICE` 만 교체.** 대조군이 성립한다는 증거:

```
device: cpu   cuda_available: True
```

H100 이 꽂혀 있고 paddle 이 그것을 보고 있는데, 일부러 쓰지 않는 상태다.

| | GPU (`gpu:0`) | CPU (`cpu`) | 배수 |
| --- | --- | --- | --- |
| 추론 p50 | **71.3 ms** | 5,656.9 ms | **79.3x** |
| 추론 평균 | 71.8 ms | 5,654.0 ms | 78.7x |
| 추론 p99 | 84.5 ms | 5,680.2 ms | 67.2x |
| 왕복 p50 | 77.4 ms | 5,664.8 ms | 73.2x |
| 처리량 | 12.81 req/s | 0.18 req/s | 71.2x |
| p99/p50 (지터) | 1.17 | 1.004 | — |
| 추론 밖 몫 | 6.2 ms (**8.0%**) | 7.4 ms (**0.1%**) | — |
| 실패 | 0 / 50 | 0 / 50 | — |

### 읽을 점

**(1) 같은 결과를 냈다.** 양쪽 모두 인식 텍스트 17개로 50건 전부 동일했다.
속도만 다르고 출력은 같으므로 비교가 성립한다. 이 값이 흔들렸다면 아래 숫자는
전부 의미가 없다.

**(2) 추론 밖 몫은 장치와 무관한 상수다.** 6.2 ms 와 7.4 ms 로 사실상 같고,
비율만 0.1% -> 8.0% 로 바뀌었다. GPU 는 추론을 79배 줄였지만 HTTP, 업로드,
큐 대기는 전혀 줄이지 못한다.

여기서 천장이 보인다. 고정 비용이 약 7 ms 이므로 **단일 스트림 처리량의
이론적 상한은 약 143 req/s** 다. 현재 12.8 req/s 이니 아직 여유가 있지만,
지금보다 10배 빠른 GPU 로 바꾸면 추론이 7 ms 가 되어 **왕복의 절반이 고정
비용**이 된다. 그 지점부터는 GPU 를 바꿔도 사용자가 느끼는 지연이 거의
변하지 않는다.

GPUaaS 운영에서 "GPU 를 더 주세요"가 답이 아닌 경우가 이것이다. 답은 배치
처리, 연결 재사용, 또는 한 장을 쪼개 여러 요청을 동시에 받는 쪽이다.

**(3) CPU 가 더 안정적이다.** p99/p50 이 CPU 1.004, GPU 1.17 이다. 느린 대신
예측 가능하다. 다만 GPU 의 지터도 절대값으로는 13 ms 라 문제될 수준은 아니다.

**(4) warmup 비용은 GPU 에만 있다.**

| | 첫 요청 | 마지막 warmup |
| --- | --- | --- |
| GPU | 268.6 ms | 78.2 ms |
| CPU | 5,855.9 ms | 5,640.0 ms |

GPU 만 3.4배 줄어든다. 다만 이 수치는 **진짜 CUDA 컨텍스트 생성 비용이
아니다.** `OCR_WARMUP=true` 라서 파드 기동 시점에 워밍업 추론이 이미 한 번
돌았고, 그 비용은 startup probe 뒤에 가려졌다. 여기 268 ms 는 이 입력 크기에
대한 cuDNN 재튜닝과 첫 메모리 할당 몫이다.

운영 관점에서는 이쪽이 더 중요한 사실이다. **probe 설계가 초기화 비용을
사용자에게서 가려 준다.** 워밍업 없이 readiness 를 통과시켰다면 첫 사용자가
그 비용을 전부 떠안았을 것이다.

## 2. 동시성 스윕 (2026-11-27)

`bench/sweep.py` 로 측정. 부하를 거는 동안 GPU(DCGM Exporter)와 파드
CPU(cgroup `cpu.stat`)를 함께 샘플링했다. 처리량만 재면 "포화됐다"까지는
알아도 **무엇이 포화시켰는지**를 모른다.

GPU 메트릭 주의: 이 설치본의 DCGM Exporter 에는 `SM_ACTIVE` / `SM_OCCUPANCY`
가 없다. 그래서 포화 판단은 `PROF_GR_ENGINE_UTIL_RATIO`(활성)과
`PROF_DRAM_UTIL_RATIO` / `PROF_TENSOR_UTIL_RATIO`(포화)로 했다.

### 2-1. 기본 설정 - 애플리케이션이 직렬화하고 있었다

`OCR_MAX_CONCURRENCY=1`, `OCR_CPU_THREADS=1`, `OMP_NUM_THREADS=1`

| 동시성 | 처리량 | 추론 p50 | 왕복 p50 | GR-Engine | DRAM/Tensor | CPU 코어 | throttle |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 11.8 | 78.2 ms | 84.6 ms | 0.00 | 0 | 0.91 | 0 |
| 2 | 15.8 | 110.8 ms | 126.8 ms | 0.02 | 0 | 0.96 | 0 |
| 4 | 16.2 | 236.5 ms | 252.6 ms | 0.08 | 0 | 0.94 | 0 |
| 8 | 16.7 | 474.2 ms | 490.1 ms | 0.08 | 0 | 0.93 | 0 |

지연이 동시성에 정확히 비례하고(85 → 127 → 253 → 490), 처리량은 멈춘다.
요청이 줄을 서고 있다는 신호다. 그런데 GPU 도 CPU 한도도 한계가 아니다.
GPU 엔진은 8%, CPU 는 1.5코어 한도 중 0.95 만 쓰고 throttle 은 0 이다.

원인은 애플리케이션 자신이었다:

```python
# workloads/inference/app/ocr.py
_predict_slots = threading.BoundedSemaphore(MAX_CONCURRENCY)   # = 1
```

**한 번에 한 건씩만 추론한다.** 이 세마포어는 CPU 벤치마크를 위해 일부러 넣은
것이라 버그가 아니다. 조건이 GPU 로 바뀌었는데 설정이 따라오지 않은 경우다.

### 2-2. 세마포어와 스레드를 풀었을 때 - 다음 벽은 CPU 한도

`OCR_MAX_CONCURRENCY=4`, `OCR_CPU_THREADS=4`, `OMP_NUM_THREADS=4`
(파드 자원은 그대로 1500m / 3Gi)

| 동시성 | 처리량 | 추론 p50 | 왕복 p95 | GR-Engine | DRAM/Tensor | CPU 코어 | throttle |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 15.81 | 56.8 ms | 64.2 ms | 0.00 | 0 | 0.95 | 0 |
| 2 | **21.85** | 80.9 ms | 101.6 ms | 0.00 | 0 | 1.37 | 1 |
| 4 | 20.17 | 174.5 ms | 251.2 ms | 0.00 | 0 | **1.47** | **48** |
| 8 | 18.91 | 387.2 ms | 512.9 ms | 0.11 | 0.01 | **1.47** | **51** |

세 신호가 같은 곳을 가리킨다.

1. **CPU 가 1.47 코어에서 천장을 친다.** 한도가 1500m 이니 정확히 거기다.
2. **`nr_throttled` 가 0 → 1 → 48 → 51 로 늘어난다.** 커널이 "한도에 걸려
   강제로 쉬게 했다"고 센 횟수다. 추측이 아니라 계측값이다.
3. **GPU 는 여전히 논다.** 엔진 활성 11%, DRAM/Tensor 1%.

`kubectl top` 으로는 1번만 보인다. 2번은 cgroup 의 `cpu.stat` 을 직접 읽어야
나오고, 그것이 "CPU 를 많이 쓴다"와 "CPU 한도에 막혔다"를 가른다.

### 2-3. 읽을 점

**병목은 한 겹씩 벗겨진다.** 애플리케이션 세마포어 → 파드 CPU 한도. 둘 다
GPU 가 아니었다. H100 을 붙여 놓고 GPU 는 10% 만 쓰면서 지연이 6배로 늘어난
상태인데, 여기서 GPU 를 더 주면 아무 일도 일어나지 않는다. 실제 GPUaaS 운영
에서 "GPU 가 느려요"로 올라오는 티켓의 전형이다.

**최적 동시성은 2다.** 그 뒤로는 처리량이 오히려 떨어진다
(21.85 → 20.17 → 18.91). 같은 1.5코어를 더 많은 스레드가 다투면서 문맥 전환과
throttle 이 늘기 때문이다. 동시성을 올리면 좋아진다는 직관이 깨지는 지점이고,
용량 산정에서 중요한 숫자다.

**단일 요청도 27% 빨라졌다** (78.2 → 56.8 ms). 추론 자체가 아니라 전처리·
후처리가 빨라진 것이다. 스레드를 1에서 4로 올렸으니까. 서버가 보고하는
"추론 시간"에 CPU 작업이 섞여 있었다는 뜻이다.

> 1절의 79배 비교는 `OCR_MAX_CONCURRENCY=1`, 스레드 1 설정에서 잰 값이다.
> 양쪽에 같은 제약이 걸려 있었으므로 비교 자체는 유효하지만, 그 숫자가
> 이 워크로드의 최대치는 아니다.

### 2-4. CPU 한도를 올렸을 때 - 세 번째 벽

`cpu: 4 / memory: 6Gi`, `OCR_MAX_CONCURRENCY=4`, 스레드 4.
동시성 8, **2000건, 75.27초** 연속 부하. 실패 0, 인식 텍스트 17개로 전부 동일.

요청 수를 2000건으로 늘린 이유는 DCGM Exporter 의 기본 수집 주기가 **30초**이기
때문이다. 5초짜리 부하로는 30초 창의 대부분이 유휴 구간이라 GPU 수치가 6배쯤
작게 나온다. 75초를 돌리면 창이 부하 구간 안에 온전히 들어간다.

| | CPU 1.5코어 | CPU 4코어 |
| --- | --- | --- |
| 처리량 | 18.91 req/s | **26.57 req/s** (+41%) |
| 추론 p50 | 387.2 ms | **276.1 ms** |
| 왕복 p50 | 412.8 ms | **299.1 ms** (-28%) |
| CPU 사용 | 1.47 / 1.5 | **1.94 / 4** |
| throttle | 51회 | **0** |
| GR-Engine | 0.11 (희석됨) | **0.20 ~ 0.30** |
| DRAM / Tensor | 0.01 | 0.01 |

**throttle 이 사라졌고 CPU 도 4코어 중 1.94 만 쓴다.** CPU 한도는 더 이상
병목이 아니다. 2-2 의 진단이 맞았다는 확인이다.

**희석도 확인됐다.** 같은 조건에서 부하만 길게 가져가니 GR-Engine 이
0.11 에서 0.20~0.30 으로 올라왔다. 진짜 값은 20~30% 다. 다만 DRAM 과 Tensor 는
여전히 1% 다 - **엔진은 25% 돌지만 그 안에서 하는 일은 거의 없다.**

### 세 번째 벽 - 다시 세마포어

CPU 도 GPU 도 한계가 아닌데 처리량은 26.57 에서 멈췄다.

```
요청 1건이 차지하는 시간 = 8 / 26.57       = 301 ms
그중 실제 CPU 시간       = 1.94 / 26.57    =  73 ms
                                   차이    = 228 ms  (기다린 시간)
```

`OCR_MAX_CONCURRENCY=4` 이므로 동시성 8 에서는 절반이 슬롯을 기다린다.
299 ms = 150 ms(처리) + 150 ms(대기) 로 계산이 맞는다.

**병목은 세 겹이었다: 세마포어 1 → 파드 CPU 한도 → 세마포어 4.
세 번 다 GPU 가 아니었다.**

### H100 한 장을 채우려면 CPU 가 얼마나 필요한가

실측값으로 역산한다.

```
GPU 엔진 시간 = 0.25 x 75.27s / 2000건  ~= 9.4 ms/건
CPU 시간      = 1.94코어 / 26.57 req/s  ~= 73  ms/건

엔진을 100% 채우는 처리량 = 1000 / 9.4   ~= 106 req/s
그만큼 돌리는 데 드는 CPU = 106 x 0.073  ~= 7.8 코어
```

**약 8코어 - 노드 하나 전체다.** 그런데 거기까지 가도 DRAM/Tensor 는 여전히
바닥일 것이다. "엔진은 바쁘지만 실제로는 일하지 않는" 상태가 유지된다.

GPU 한 장에 파드 하나를 붙이는 배치가 이 워크로드에는 맞지 않는다는 뜻이다.
맞는 방향은 둘이다:

1. **GPU 를 쪼개 여러 파드에 나눠 준다** (MIG / time-slicing). 각 파드가 자기
   CPU 를 갖는다.
2. CPU 전처리를 GPU 로 옮긴다 (DALI 등). 범위가 크게 늘어난다.

이 프로젝트의 다음 단계는 1번이고, 위 숫자가 그 근거다.

## 3. GPU 포화도

전 구간에서 GPU 는 포화와 거리가 멀었다.

| 지표 | 최대 관측값 | 뜻 |
| --- | --- | --- |
| `GR_ENGINE_UTIL` | 0.30 | 엔진이 활성인 시간 비율 30% |
| `DRAM_UTIL` | 0.01 | 메모리 대역폭 1% |
| `TENSOR_UTIL` | 0.01 | 텐서 코어 1% |
| `FB_USED` | 921 MB | 94GB 중 **약 1%** |

(GR_ENGINE 은 75초 부하에서 잰 값. 짧은 부하에서는 수집 주기 30초에 희석되어
0.11 로 나왔다.)

메모리 921MB 는 유휴 시 3.47MB 에서 올라온 값으로, 드라이버가 센 수치다.
애플리케이션이 `/info` 로 "GPU 를 쓴다"고 말하는 것과는 다른 층위의 증거다.

**H100 NVL 한 장을 이 워크로드 하나에 통째로 주는 것은 과하다.** MIG 로
쪼개면 가장 작은 조각도 12GB 인데 그것조차 13배 과하고, 연산 쪽도 10% 선이다.
다만 그 결론을 확정하려면 `SM_ACTIVE` / `SM_OCCUPANCY` 가 필요하다 -
현재 exporter 에 없으므로 counters 설정 보강이 선행 과제다.
