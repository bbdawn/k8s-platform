# 측정

## 왜 이렇게 재는가

이 벤치마크가 답하려는 질문은 "H100 이 CPU 보다 빠른가"가 아니다. 그건
당연하고, 숫자를 보지 않아도 안다. 실제 질문은 이것이다:

> **이 workload 에서, GPU 를 붙이면 무엇이 얼마나 바뀌고, 어디서부터 GPU 가
> 더는 답이 아닌가.**

그래서 설계가 이렇다.

### 1. 같은 노드, 같은 이미지, `OCR_DEVICE` 하나만 바꾼다

GPU VM 은 8 vCPU / 16GB 로 CPU worker 와 같은 flavor 다. 그런데도 비교를
노드를 갈라서 하면 CPU 모델, 메모리 대역폭, NUMA 배치가 전부 섞인다. 차이가
나와도 장치 덕분인지 머신 덕분인지 분리할 수 없다.

GPU 이미지에 들어간 `paddlepaddle-gpu` 는 `OCR_DEVICE=cpu` 로도 돈다. 그래서
**이미지까지 고정한 채** 장치 하나만 바꿀 수 있다. 이것이 이 저장소에서
GPU/CPU 두 이미지를 따로 두면서도 비교는 GPU 이미지 안에서 하는 이유다.

```bash
# GPU 노드에서 CPU 로 돌리기 (대조군)
kubectl -n ocr-bench set env deploy/ocr-gpu OCR_DEVICE=cpu
```

CPU worker 에 올라간 `ocr` 배포는 "CPU 이미지가 제대로 도는가"를 확인하는
용도이지, 장치 비교의 대조군이 아니다.

### 2. warmup 을 통계에서 뺀다

GPU 첫 요청은 CUDA 컨텍스트 생성, cuDNN 자동 튜닝, 메모리 풀 확보를 혼자
떠안는다. 수십 배 느리다. 그 한 번이 평균에 들어가면 "GPU 가 CPU 보다
느리다"는 결론이 나온다 - 실제로 흔히 보는 오측이다.

`load.py` 는 warmup 구간의 첫/마지막 지연을 따로 찍어 준다. 그 둘의 차이가
초기화 비용이고, 그 자체로 기록할 가치가 있다.

### 3. 평균이 아니라 분위수를 본다

평균은 꼬리를 숨긴다. GPU 는 평균이 낮아도 커널 실행이 몰릴 때 p99 가 튄다.
서비스 품질을 말할 때 의미 있는 숫자는 p95/p99 쪽이다.

### 4. 추론 시간과 왕복 시간을 둘 다 기록한다

서버가 `elapsed_ms` 로 순수 추론 시간을 돌려준다. 클라이언트는 왕복을 잰다.
**둘의 차이가 HTTP, 업로드, 큐 대기 몫**이다.

이 차이가 이 벤치마크에서 가장 볼 만한 부분이다. GPU 로 추론이 빨라지면
추론 밖 몫이 상대적으로 커지고, 어느 순간 추론이 아니라 그 주변이 병목이
된다. 그 전환점을 지나면 GPU 를 더 좋은 걸로 바꿔도 사용자가 느끼는 지연은
거의 안 바뀐다 - GPUaaS 에서 "GPU 를 더 주세요"가 답이 아닌 경우가 바로
이것이다.

### 5. 입력을 고정한다

`sample.png` (640x464, 한글 운송장 형태) 하나만 쓴다. 요청마다 다른 이미지를
쓰면 글자 수에 따라 지연이 흔들려 장치 차이와 구분되지 않는다. 결과의
`인식 텍스트 수` 가 매번 같은 값 하나로 나오는지 확인할 것 - 여러 값이
나오면 입력이나 전처리가 고정되지 않았다는 신호다.

이미지는 `640` 짧은 변 기준으로 `OCR_MAX_IMAGE_SIDE=640` 와 맞춰 두어서
서버에서 리사이즈가 일어나지 않는다.

## 쓰는 법

의존성 없음. cp 노드의 `python3` 로 바로 돈다.

```bash
# 단일 동시성 - 순수 지연 비교용
python3 bench/load.py --url http://10.240.0.25:30801 -c 1 -n 100 \
  --label gpu-c1 --json-out bench/results/gpu-c1.json

# 동시성을 올려 가며 - 포화점 찾기
for C in 1 2 4 8; do
  python3 bench/load.py --url http://10.240.0.25:30801 -c $C -n 100 \
    --label gpu-c$C --json-out bench/results/gpu-c$C.json
done
```

`--json-out` 은 그 시점의 `/info` 를 통째로 같이 저장한다. 나중에 결과를 볼 때
"어떤 장치, 어떤 드라이버, 어떤 paddle 빌드에서 잰 수치인가"가 수치만큼
중요하기 때문이다.

## 측정 중에 GPU 를 들여다보기

```bash
# [k8s-gpu] 1초마다
nvidia-smi dmon -s um
```

`sm` 열이 SM 점유율, `mem` 이 메모리 대역폭 사용률이다. `DCGM_FI_DEV_GPU_UTIL`
(= `nvidia-smi` 의 `GPU-Util`) 은 "커널이 돌고 있다"만 뜻하지 포화를 뜻하지
않는다. 1% 짜리 커널이 쉬지 않고 돌아도 100% 로 나온다. 진짜 포화 신호는
`DCGM_FI_PROF_SM_OCCUPANCY` 와 `DCGM_FI_PROF_PIPE_TENSOR_ACTIVE` 다.

이 workload 에서 `GPU-Util` 은 높은데 `SM_OCCUPANCY` 가 낮게 나올 가능성이
크다. OCR 검출/인식 모델이 작아서 H100 의 SM 을 다 채우지 못하기 때문이다.
그게 사실이면 **MIG 로 쪼개 여러 파드에 나눠 주는 것이 맞다**는 근거가 된다 -
ROADMAP 의 MIG 실험이 거기서 출발한다.
